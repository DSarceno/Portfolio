## 2. Theory / methods / features integrity — 🟢 RESOLVED (was one deviation)

> **Resolution (2026-06-29):** the deviation below was a real bug (multinomial stage-feature
> train/serve skew). It is now fixed in code **and** the stack was redeployed via a deliberate
> backtest-gated re-tune: the multinomial weight is back to the designed **0.20** (four-model blend)
> and calibration moved isotonic → **sigmoid**. The narrative below is kept as the diagnosis record;
> the live system now matches the four-model design.

**Intact and as designed:** Skellam H/D/A + Dixon–Coles exact scorelines; Elo/pi/form rating
ensemble; XGBoost; sigmoid (Platt) calibration; LASSO feature selection; squad-value match features; the
leakage-free cross-tournament backtest as the arbiter; the four-profile quiniela decision layer.
The "freeze models during the tournament" policy now enforced is textbook-correct (validate
pre-event, freeze, update only ratings/state).

**Deviation — the multinomial model is excluded from the live blend.** Root cause (found 2026-06-29,
fixed in code): the tournament-stage indicators `stage_group` / `stage_knockout` are **identically 0
across the entire historical training set** — the Kaggle international feed tags every historical
match `stage="historical"`, so the keyword detector never fires, even on the 192 WC / 153 EURO / 144
Copa matches in training. They only become 1 at *serving* time, for 2026 fixtures. That is a textbook
**train/serve skew**: `StandardScaler` learns a (near-)zero `scale_` for a constant feature, so when
it flips to 1 for a live knockout fixture the standardized value explodes to ~+100 SD and dominates
the linear logit, saturating the softmax to ~99% the away team for *every* knockout fixture (verified:
all 15 upcoming ties → away, mean 0.978; `stage_knockout` scaled +104 vs next feature +3.5). The
mid-tournament retrain merely *triggered* a latent bug: pre-tournament those features had **exactly**
zero variance (scale→1.0, harmless); the retrain pulled a handful of 2026 group/knockout rows into the
training fold (`temporal_split` puts 2026 in train), giving tiny non-zero variance (scale 0.01) and the
explosion. XGBoost/Poisson are immune (no standardization). The backtest never caught it because the
historical hold-out folds are *also* all-`historical` (stage indicators = 0 there too) — the bug is a
live-serving-only phenomenon.

**Fix (code):** `MultinomialOutcomeModel` now (a) drops features whose single most-frequent training
value covers ≥99% of rows (near-constant ⇒ unlearnable by a standardized linear model) and (b) clips
standardized values to ±8 SD as defense-in-depth. Verified live: the 15 upcoming knockout ties now
get sane, signal-tracking probabilities (Germany–Paraguay H 0.51; France–Sweden H 0.62; Norway over
Ivory Coast A 0.42; mean H/D/A 0.48/0.33/0.19 — no saturation). Regression test:
`tests/unit/test_models.py::test_multinomial_drops_near_constant_training_feature`.

**Corrected impact (controlled A/B backtest, 2018+2022, leakage-free — same data/settings, only the
multinomial weight toggled):**

| Config | log-loss | Brier | RPS | accuracy |
| --- | --- | --- | --- | --- |
| 3-model (multinomial = 0) | **0.9867** | 0.1946 | 0.2079 | 0.547 |
| 4-model, **fixed** multinomial = 0.20 | 0.9888 | 0.1950 | 0.2077 | 0.555 |
| uniform baseline | 1.0986 | — | — | 0.33 |

Per fold the multinomial helps 2018 and hurts 2022 by ~±0.005 log-loss (n=64 each) — i.e. **roughly
neutral, within fold noise**. ⚠️ **Correction to the earlier draft of this audit:** it reported the
multinomial "recovers ~0.007 log-loss" by comparing a freshly-run 3-model (0.9977) against a *stale
documented* 4-model figure (0.9905). That was not a controlled comparison (different data vintage /
settings). The controlled A/B above is the correct measurement: there is **no material log-loss to
recover** — the multinomial is a wash. So excluding it costs essentially nothing, and the value of the
fix is **robustness** (the model can no longer explode on a stage-skewed feature), not accuracy.

**Deployed via re-tune (2026-06-29).** Rather than wait for post-tournament, a deliberate
backtest-gated re-tune was run: `run_pipeline.py` → `train_models.py` regenerated the whole stack with
the fixed code (the multinomial now drops `stage_group`/`stage_knockout` and fits on 17 features;
calibrator fit on 1002 validation samples). The weight was re-decided from a holdout grid (0.0/0.10/0.20,
all within fold noise on log-loss; 0.20 best accuracy) and **restored to the designed 0.20**. The live
knockout probabilities are now sharp and all-distinct (Argentina 0.756, England 0.740, France 0.699,
Germany 0.652; no saturation, no step-ties). The previous models were backed up to
`models_backup_<ts>/` for rollback. `MultinomialOutcomeModel.__setstate__` still backfills the guard
fields when unpickling any pre-fix artifact, so loading an old pickle can never crash the live path.
**The matchday loop remains frozen** — `update_matchday.bat` still excludes `run_pipeline`/`train_models`;
this was a one-off, sanctioned re-tune (see RETRAINING_GUIDE), not a change to the daily flow.

**Second bug found and fixed during this work — `predict_knockout.py` ignored the config blend
weights.** It built its `MatchPredictor` *without* a blender, so it silently used `BlendWeights()`
defaults (**multinomial 0.20**) instead of `BlendWeights.from_config` — meaning the live
`knockout_predictions.csv` was blended with the degenerate multinomial at 20% **despite** the config
exclusion. Every other prediction path (group stage, scorelines, quiniela, simulation, API) correctly
used `from_config`; knockout was the lone exception, so the group-stage forecast looked sharp while the
knockout CSV stayed poisoned (flat, away-tilted, many identical values). Fixed to read
`from_config`; after the fix the knockout probabilities are sharp and sensible (England 0.88, Argentina
0.88, France 0.76, Germany 0.70). Regression test:
`tests/unit/test_predict_knockout_weights.py`. This is also why notebook 05 (which computes its own
symmetrised pairwise probabilities) looked correct while the exported CSV did not.

> **Interpreting the log-loss numbers.** Log-loss (multiclass cross-entropy) is the mean of
> `-ln(p[actual outcome])` over all matches, where each match's H/D/A probabilities sum to 1.
> **Lower is better; 0 is perfection.** The reference point is the *no-skill* baseline of always
> predicting 1/3–1/3–1/3, which scores `ln 3 = 1.0986`. Any useful model must beat it. Both blends
> (≈0.987–0.989) sit well below 1.0986, retaining ~92% of the edge over chance; the ~0.002 gap
> between them is per-match noise (assigning the true outcome a probability ~0.2% different on
> average), not a meaningful difference.

**Doc/theory consistency (#4 — done):** the live blend is once again the **four-model** ensemble the
articles and MODELING_GUIDE describe, so the narrative is accurate again. MODELING_GUIDE, README,
OPERATIONS_RUNBOOK, RETRAINING_GUIDE, TROUBLESHOOTING and CLAUDE.md were updated to reflect the
restored multinomial weight (0.20), the near-constant feature guard, and the sigmoid calibration.

## 4. Other observations — 🟢 minor

- **Isotonic calibration step-collapse — ✅ fixed (#5).** A few even mid-table ties shared an identical
  calibrated probability (e.g. 0.4062), an isotonic step-function artifact. A holdout A/B (calibrator
  fit on 2018, n=64; evaluated on 2022) showed isotonic was not just step-y but *unstable* on small
  data — log-loss 1.45 vs sigmoid 1.04 (uncalibrated 1.00) — confirming theory (isotonic overfits small
  calibration sets). Switched to **sigmoid (Platt)** via `config/model_params.yaml::calibration.strategy`
  (now read by `train_models.py`). Live knockout probabilities are now all-distinct (15/15) and smooth.
- **Data integrity:** canonical table clean — 11,934 rows, 0 duplicate `(date,team_a,team_b)` keys;
  the SA–Canada result merged correctly onto the fixture (no orphan/phantom).
